### `dfc0d6324` 用户设置更新竞态可回滚已消费配额（安全通告合并修复，fork 残余三个子项）【复核：属实】

上游修复内容：①`PUT /api/user/self` 任意 JSON 反序列化为 `model.User` 全量 Updates（mass assignment 可改 quota）；②设置更新走全行 Update，读-改-写竞态内用过期快照覆盖 `quota`/`used_quota`/`request_count`；③`updateUserCache` 把快照 Quota 写回缓存；④`PUT /self` 缺 `CriticalRateLimit`。

涉及文件（迁移后现路径）：
1. `internal/store/user/user.go:423-439`（`Update` 为 `DB.Model(user).Updates(newUser)` struct 非零字段回写，无 `Omit("quota","used_quota","request_count")`）
2. `internal/store/user/user_cache.go:64-75`（`updateUserCache` 经 `RedisHSetObj` 反射全字段写入含 Quota 的 UserBase）
3. `internal/controller/user.go:1043-1177`（`UpdateUserSetting` 取全量快照后调 `user.Update(false)`）
4. `internal/router/api_router.go:76/:96`（`PUT /user/self`、`PUT /user/setting` 无 CriticalRateLimit）

原因（复核后现状证据）：
1. 子项①fork 已免疫：`UpdateSelf` 用 `cleanUser` 白名单重建落库对象，仅 Id/Username/Password/DisplayName（`internal/controller/user.go:601-617`），请求体中恶意传入的 quota 不会进入 SET 子句。
2. 子项②③成立且已完整推演：`UpdateUserSetting` 在 `:1125` 以 `GetUserById(userId, true)` 取全量快照，改 setting 后 `:1170` 调 `user.Update(false)`。`Update` 内部虽先 `newUser := *user` 再 `First` 重读最新行，但重读值不流入 SET——GORM `Updates(struct)` 写入的是 `newUser`（快照）的全部非零字段，旧快照的 `quota`/`used_quota`/`request_count`/`role`/`status`/`group` 均被回写。而中继计费对这些字段的修改全部是原子增量（`DecreaseUserQuota` `user.go:742-765`、`UpdateUserUsedQuotaAndRequestCount` `:788-813`），窗口 `[快照读取, UPDATE 提交]` 内已提交的扣费被回滚——**用户可借此恢复已耗额度**。Redis 侧 `updateUserCache` 全量 HSet 后控制器随即失效缓存，最终缓存与被污染的 DB 一致。触发仅需普通用户认证（会话或 access token + 匹配的 `New-Api-User` 头），全程无事务/行锁/乐观锁/条件更新任何一层防护。
3. 复核补充的放大面：同一回写窗口还可回滚并发管理操作（封禁/改组）；同族风险面覆盖一切走 `User.Update` 的自服务接口（含 `EmailBind`），修复时应统一收口而非逐点打补丁。
4. 子项④成立但需注记：两条路由确实缺 `CriticalRateLimit`（同组 register `:59`、reset_password `:44-45`、topup `:90` 均有挂）；它们仍受 `/api` 组级 `GlobalAPIRateLimit`（IP 级，默认 180 次/180 秒）约束，缺的是更严的关键限流，并非完全无限流。

应当表现为：
1. 新增只更新 setting 列的 `UpdateUserSetting(userId, setting)`；`Update`/`Edit` 路径 `Omit("quota","used_quota","request_count")`；`updateUserCache` 不写 Quota（配额统一由原子增量路径维护）；`PUT /user/self`、`PUT /user/setting` 挂 `CriticalRateLimit`；参照上游补 user_update 回归测试（先证伪再修复）。

### `47ba9d2c6` 充值入账守护钱包额度上限（复核：int32 天花板前提被实验证伪，条目降级重写为"入账上限守护与极端值换算校验"）

> 复核结论：原断言"fork 的 `users.quota` 列为 `type:int`（MySQL 下 int32 上限约 21.47 亿；
> QuotaPerUnit=500000 时约 $4300 即溢出，可溢出回绕成负数"**前提错误**。经用仓库锁定版本
> （gorm v1.31.2 / mysql driver v1.6.0 / postgres driver v1.6.2 / glebarez-sqlite v1.11.0）
> 实际生成 DDL 验证：`gorm:"type:int"` 作用于 Go `int` 字段时解析为 DataType=`"int"` 且
> Size 默认置 64，MySQL/PostgreSQL 均生成 **bigint**，SQLite 为 64 位 INTEGER。三库均不存在
> int32 列，$4300 余额天花板不存在；充值路径在任何库下都不存在"回绕为负"（MySQL 表达式
> 溢出报 ERROR 1690 回滚且与 sql_mode 无关、PostgreSQL 报 22003 回滚、SQLite 见下）。
> 本条按实际风险降级，与 `2a0ce3475` 合并处置。

仍然成立的事实（复核后）：
1. 全库无充值容量守护：`ValidateTopUpQuotaCapacity` 或等价函数不存在（最接近的 `validateTopUpCallback` `internal/store/topup/topup.go:75` 只校验渠道/金额/状态，不校验容量）；四处入账均为裸 `quota + ?` 且无 `WHERE quota <= ?` 守护——Stripe 回调 `topup.go:175`（float64 直传）、易支付 `:244`、管理员补单 `:475`、兑换码 `internal/store/redemption/redemption.go:145`。防重复入账依赖订单状态条件翻转 + 订单级互斥锁，守护对象不是余额上限。
2. 易支付下单/询价无金额上限：`RequestEpay`（`internal/controller/topup.go:126-195`）与 `RequestAmount`（`:273-297`）仅校验下限（`:133-136`/`:281-284`）。
3. 极端值下的真实失败模式（边界在 2^63 而非 2^31）：PostgreSQL 侧 Stripe 非整 float 参数因 `PreferSimpleProtocol` 文本化报 22P02，webhook 5xx 无限重投、已付款不入账；SQLite 侧越过 int64 或混入小数后**静默转为 REAL，该行 quota 后续读取 Scan error（行级数据损坏）**。
4. Go 层换算回绕（复核新发现）：`int(dAmount.Mul(...).IntPart())`（`topup.go:222-224`/`:447-453`）中 `IntPart()` 取低 64 位——负回绕被 `quotaToAdd <= 0` 拦截，但**正回绕**绕过检查（实测 Amount=46,116,860,184,272 × QuotaPerUnit=500000 → `IntPart()=4,611,686,018,426,448,384`，入账错误巨量额度）。实际触发需真实支付对应金额（易支付回调校验金额一致）或管理员补单（补单不校验是否付款），实用可利用性低。

应当表现为：
1. 与 `2a0ce3475` 合并处置：下单/询价接口补上限与授信额度换算范围校验（`IntPart()` 改带范围检查的换算，超范围显式报错）；Stripe `Recharge` 的 float64 直传（`topup.go:174-175`）一并收敛为 decimal；余额容量守护（`WHERE quota <= ?` 条件 UPDATE）作为纵深防御可选，不再按"$4300 实用溢出"排 P0。

> **处置注（2026-08-21）**：第 4 点 Go 层换算回绕与 Stripe float64 直传已落地——新增
> `common.DecimalToInt`（`internal/common/decimal_int.go`：decimal 精确比较
> `math.MaxInt/MinInt` 后取整，超界显式报错），`internal/store/topup/topup.go` 三处结算
> 换算（易支付回调、管理员补单双分支、Stripe `Recharge`）全部收敛到该路径，`Recharge`
> 同时消除 PostgreSQL 22P02 与 SQLite REAL 化风险。回归测试
> `internal/store/topup/topup_overflow_test.go` 在 `GOARCH=386` 下先证明旧代码对
> $8599 × 500000 静默入账回绕值 4,532,704、修复后 fail-closed（订单保持 pending、
> 额度不变）。**未落地**：下单/询价接口（`RequestEpay`/`RequestAmount`）支付前的
> 授信额度校验与金额上限（结算侧已 fail-closed，剩余为体验问题）；余额容量守护
> （纵深防御可选）。relay 按次计费等同类 `int(IntPart())` 转换点默认配置下已数值论证
> 安全，留待后续统一加固时收敛到 `DecimalToInt`。
