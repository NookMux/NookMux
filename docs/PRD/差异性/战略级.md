## ClickHouse 日志库链 `6dc4030fd` + `f84b7d591` + `df44a75d5`

涉及文件：`common/database.go`、`model/main.go`、`model/log.go`、go.mod（clickhouse 驱动）等整链。

现状：fork 仅存死变量 `UsingClickHouse = false`（`internal/common/database.go:13`），日志库仅 SQLite/MySQL/PG；LIKE 均为 `ESCAPE '!'` 三库兼容写法、清理为同步端点 + 分批删除。

应当表现为：若决策引入，必须整链移植（类型化 DatabaseType、clickhouse DSN、排序/request_id 兜底/TTL/统计适配、单次 mutation 删除、LIKE 反斜杠转义），不能只拿补丁。fork 现有三库承诺与 `.env.example` 文档需同步。**纯容量决策，单实例中小部署无痛点。**

## 节点/系统任务基建链 `354d0fedb` + `2cbdfa039` + `537719229` + `a72e5082e` + `a162163b4`（+ `f8cfbfa4d`）

涉及文件：`common/node_identity.go`、`model/system_task.go`/`system_instance.go`、`service/system_task.go`、controller/router、前端 `features/system-info/` 等整链。

现状：fork 无 NodeName 概念（仅 NODE_TYPE master/slave）、无 system_task/system_instance 表、无任务运行器；渠道自动测试是主节点 sleep 循环。上游该链迁移的任务源（midjourney 轮询/异步任务轮询/渠道上游更新）fork 均已删除，**实际可接入的只有渠道测试一个，+2561/-582 的移植收益大幅缩水**。

应当表现为：仅当 fork 有多实例横向扩展规划时，作为统一战略分支设计（节点身份 → 实例心跳/面板 → 任务运行器 → 陈旧实例清理），接入点按 fork 代码重写，且遵守 fork 规范（常驻资源保守、RecordAudit、i18n、环境变量文档）。`f8cfbfa4d`（删除旧清理端点）在 fork **不可移植**——fork 的 `DELETE /api/log/` 是唯一清理入口且已审计化。

## 细粒度管理员权限（casbin RBAC）`4aee5f7d5`

涉及文件：上游 `service/authz/*`（11 文件）、`model/casbin_rule.go`/`authz_role.go`、`middleware/auth.go`、路由与前端权限编辑器，+2776 行。

现状：fork 仅三角色 + 路由整体挂 AdminAuth/RootAuth；敏感操作已用另一方式加固（如 GetChannelKey 要求 RootAuth+SecureVerification），但"某管理员只授渠道编辑、不给删除/密钥查看"这类粒度做不到。上游提交中的审计归属修正部分对 fork 不适用（fork 自有审计体系操作者归属天然正确）。

应当表现为：若产品需要管理员分权，单独分支引入 casbin（需过三库兼容）、权限注册表、RequirePermission 逐路由映射、前端权限编辑器；属方向性产品决策。

## 无状态 dashboard 令牌与会话管控 `31d70fca3`（#6329）

涉及文件：上游 `service/auth_token.go`、`model/user_session.go`、`controller/auth_session.go`、`middleware/auth_origin.go` 等后端 50+ 文件与前端 auth-store/refresh 协调。

现状：fork 仍用 gin cookie 会话（`internal/app/server.go:129-138` cookie store、`internal/middleware/auth.go:52`），无短时效令牌、无会话列表/撤销。fork 的替代安全模型是每请求查库重验 role/status/group（封禁/降权即时生效），但 cookie 被盗即长期有效、无会话可观测能力。

应当表现为：
1. 是否跟进"无状态 dashboard 令牌"路线属专项架构决策；若跟进涉及 15 分钟 JWT access token + 刷新轮换 + 重放检测 + 服务端会话表 + 前端 refresh 协调的完整迁移。批次内的 `172114422`（refresh 容错，见[修复](修复.md)篇「重试 / 错误 / 限流」节）即依附此架构。
