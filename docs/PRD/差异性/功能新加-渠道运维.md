## `efd6c445a` + `5d3423bec` 渠道测试模式体系统一（scheduled_all / auto_ban_only / passive_recovery）（合并批）

> 本条为拆分时合并的「结论相反、应同批落地」批次：原「功能新加 / 渠道 / 运维」的
> `efd6c445a` 与原「功能新加 / 前端体验」的 `5d3423bec`（见
> [功能新加 · 前端体验](功能新加-前端体验.md) 篇末并入注）对同一 `ChannelTestMode` 字段给出
> 不一致的枚举设计且互为前置依赖，已并为一条。

涉及文件：
1. `setting/operation_setting/monitor_setting.go` → `internal/config/operation/monitor_setting.go:10-13`（仅两字段，无 `ChannelTestMode`）
2. `controller/channel-test.go` → `internal/controller/channel_test_handler.go`（`testAllChannels` 定义于 :1539，签名多 `*gin.Context`；无按模式筛选）
3. 前端 `monitoring-settings-section.tsx` + i18n

原因（两条对同一字段的结论不一致，已合并统一）：
1. `efd6c445a`（被动渠道监控模式）把设计收敛为 `channel_test_mode` 两值枚举（scheduled_all / passive_recovery）：passive 模式只重测被自动禁用的渠道、绝不自动禁用渠道，减少主动探活对健康渠道的计费消耗。
2. `5d3423bec`（仅自动禁用渠道的测试模式）以上一条为前置（上游 #5592），却把同一字段设计为三值枚举（scheduled_all / auto_ban_only / passive_recovery），并追加"手动禁用渠道一律跳过"。两条对同一配置字段的枚举口径不一致，且互为前置依赖，分开落地必然返工——应按上游最终态一次到位。
3. fork 的自动渠道测试目前只有"全量定时测试"一种模式，无渠道测试模式体系，两条所述能力均缺失。

应当表现为：
1. `ChannelTestMode` 三值枚举（scheduled_all / auto_ban_only / passive_recovery）一次落地：自动测试按模式筛选渠道，手动禁用渠道一律跳过；passive 模式仅测 ChannelStatusAutoDisabled 渠道且绝不自动禁用。fork 的 testAllChannels 签名多 `*gin.Context`（i18n），需按 fork 结构拆分。
2. 渠道测试并发 `4add708eb` 见 [修复](修复.md) 篇「性能 / 健壮性」节，同属渠道测试体系，建议与本条一并设计。
