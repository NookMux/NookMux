# 计费重构验收标准（勿提交）

## 验收范围

1. 验收范围为 [计费 PRD](计费.md) 的阶段 0～5，以及本文规定的历史数据迁移、旧 Token 总量列删除、Token 统计与导出读取切换。
2. 本文与 PRD 不一致时，以本文为验收依据。本文描述目标要求，不代表当前实现已经通过验收。
3. `billing_details` 是持久化 Token 用量的唯一权威来源；JSON 内全部 Token 字段固定存在，值为非负整数，缺失的可选拆分记 `0`。
4. 历史 Token 数据在服务接收流量前迁移；完成迁移后删除 `PromptTokens`、`CompletionTokens` 对应的 `prompt_tokens`、`completion_tokens` 数据库列，不保留旧 Token 存储和业务回退读取。
5. `Quota` 保留为日志中的实际结算额度。`Other` 保留价格、倍率、诊断等职责，不再保存或提供由 `billing_details` 接管的独立 Token 明细。
6. service tier 差异计费留待后续适配，不作为本次完整支持的验收项；已有响应层级记录、请求透传和历史快照展示不得丢失。
7. 阶段 6 的模型广场展示优化及阶段 7 的后续专项工作不在本次范围；阶段 0～5 所需的测试、联调和验收必须在本次完成。

## 横切验收

1. SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6 的空库初始化、历史库升级、重复启动迁移分别验证；同库日志与独立 `LOG_SQL_DSN` 日志库行为一致。
2. 迁移幂等；失败时阻断启动和业务流量，不得在迁移未完成时继续读写日志。
3. 各阶段具备独立编译、测试与回滚方案；涉及历史迁移和删除列的回滚必须包含数据库恢复步骤。
4. 归一化失败、上游无 usage、计费配置缺失分别可观测；错误信息不得包含 secrets，不得吞错或伪造成功。
5. 客户端协议转换及响应 usage 语义保持既有行为；计费读取真实上游用量，不依赖客户端转换后的语义猜测。
6. 后端执行 PRD 各阶段相关目标包测试；前端改动执行 `bun run typecheck`、`bun run lint`、`bun run build`；新增文案补齐中英文 i18n。
7. 各项验收附必要的代码、测试或实际请求证据，状态明确标为“通过”“失败”或“未验证”。单库通过不得代替三库验证，辅助函数测试不得代替实际入口接入验证。

## 验收环节一：数据库模块（阶段 0）

### 存储与职责

1. 新增独立 `billing_details` 列，使用 `text` 保存 UTF-8 canonical JSON；不得把现有其他列改写为 JSON 存储。
2. JSON 编解码使用 `pkg/jsonx`；新日志写入前校验 schema、数值与包含关系。
3. 有 Token 用量的消费记录写入规范 JSON；无 Token 用量的记录保持该列 NULL，不以全零 JSON 冒充已记录用量。存在明确全零 usage 时允许保存合法全零 JSON。
4. 是否写入以本条记录有无 Token 用量为准；纯工具费、违规费、图片生成调用费、文件检索费、定制音色和模型测试费等不得仅因入口名称而生成 Token 明细。
5. `Quota` 保存最终结算额度；价格、倍率、费用快照和诊断信息保留原有职责，不写入 `billing_details`。
6. `Other` 中的价格快照可保留解释费用所需的组件计价数量，但不得作为 Token 明细、总量或 TPM 的替代来源。

### 历史迁移与旧列删除

1. 升级前备份实际日志库，停止并排空旧版主从节点、后台日志写入和批量队列；不支持旧、新写入节点混跑。
2. 新版 master 在接收流量前执行迁移。历史迁移允许读取旧 `Other` Token key 和旧输入、输出总量列，恢复本文规定的 Token 数据。
3. 已有 `billing_details` 同样按本文最终字段语义、完整数字结构和总量约束检查；不得仅因列非空或存在旧完成标记就跳过本次升级。
4. 可选拆分缺失时记 `0`；文本输入、文本输出按本文公式恢复。已有合法数据不得被无依据覆盖；不同来源之间的矛盾必须显式阻断并给出可定位的记录信息。
5. 历史记录没有 Token 用量时保持 NULL。迁移前后实际结算额度、价格快照、倍率、诊断及其他非 Token 数据保持不变。
6. 历史转换和校验完成后，清除 `Other` 中已接管的独立 Token key，再删除 `prompt_tokens`、`completion_tokens` 两个旧列；不得在恢复历史数据前删除来源列。
7. 移除旧列对应的模型字段、运行期读写、查询表达式和统计依赖。旧字段只允许出现在识别和迁移旧数据库所需的升级代码中。
8. 新日志不向 `Other` 双写独立 Token 明细；迁移后的读取端不从 `Other`、旧列或价格快照反推 Token 数据。
9. 同库与独立日志库均在实际日志库执行迁移和记录完成状态；slave 不执行迁移，只在目标结构与完成状态检查通过后启动。
10. 验证批次中断、重启续迁、完成标记写入失败，以及删除旧列前后的中断恢复。完成标记必须对应最终结构，后续正常重启不得重复全表回填。
11. 导入旧格式数据必须走受控升级流程，不得绕过迁移把旧格式记录加入已经切换的业务读写路径。
12. 回滚先停止新版本读写，再恢复与旧二进制匹配的数据库备份；删除列后不得仅切换二进制恢复服务。

## 验收环节二：数据解析（阶段 1）

### 上游语义与归一化

1. 同一请求的实际上游用量只归一化一次，生成内存 `BillingUsage`，供结算与 `billing_details` 序列化共同使用；内部来源和诊断字段不进入 Token JSON。
2. 来源由上游响应解析路径显式标识，不通过 `FinalRequestRelayFormat` 反推。Claude 原生、AWS Bedrock、OpenRouter Claude 风格返回按同一 Claude 语义处理。
3. 各规范的核心总量与缓存来源如下；供应商原始模态明细还需按缓存包含关系转换为最终计价数量。


| 语义      | Claude Messages                                                        | OpenAI Chat Completions                      | OpenAI Responses                          | Gemini                                       |
| ------- | ---------------------------------------------------------------------- | -------------------------------------------- | ----------------------------------------- | -------------------------------------------- |
| 输入侧总量   | `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` | `prompt_tokens`                              | `input_tokens`                            | `promptTokenCount`                           |
| 普通输入总量  | `input_tokens`                                                         | 输入侧总量减缓存读取、写入                                | 输入侧总量减缓存读取、写入                             | `promptTokenCount - cachedContentTokenCount` |
| 输出总量    | `output_tokens`                                                        | `completion_tokens`                          | `output_tokens`                           | `candidatesTokenCount + thoughtsTokenCount`  |
| 缓存读取    | `cache_read_input_tokens`                                              | `prompt_tokens_details.cached_tokens`        | `input_tokens_details.cached_tokens`      | `cachedContentTokenCount`                    |
| 缓存写入    | `cache_creation_input_tokens`                                          | `prompt_tokens_details.cache_write_tokens`   | `input_tokens_details.cache_write_tokens` | 无标准字段，记 `0`                                  |
| 5m 写入分档 | `cache_creation.ephemeral_5m_input_tokens`                             | 按无分档规则处理                                     | 按无分档规则处理                                  | `0`                                          |
| 1h 写入分档 | `cache_creation.ephemeral_1h_input_tokens`                             | 无标准分档，记 `0`                                  | 无标准分档，记 `0`                               | `0`                                          |
| 推理输出    | `output_tokens_details.thinking_tokens`（实际返回时）                         | `completion_tokens_details.reasoning_tokens` | `output_tokens_details.reasoning_tokens`  | `thoughtsTokenCount`                         |


1. 模态与审计字段来源如下。上游原始 `text_tokens` 或 TEXT 模态明细不直接替代本文定义的 `text_input`、`text_output`；最终文本数量按总量与已知独立模态计算。


| 明细                     | 实际来源与要求                                                                                      |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| OpenAI Chat 输入图片、音频、文本 | `prompt_tokens_details.image_tokens`、`audio_tokens`、`text_tokens`                            |
| OpenAI Chat 输出音频、文本    | `completion_tokens_details.audio_tokens`、`text_tokens`                                       |
| OpenAI Chat prediction | `completion_tokens_details.accepted_prediction_tokens`、`rejected_prediction_tokens`；仅作输出审计拆分 |
| OpenAI Responses 模态    | 不虚构标准 usage 中不存在的文本、图片、音频拆分；按输出总量与推理字段处理                                                     |
| Gemini 输入模态            | `promptTokensDetails[modality=TEXT/IMAGE/AUDIO/VIDEO/DOCUMENT].tokenCount`                   |
| Gemini 缓存模态            | `cacheTokensDetails`；有明确数据时从对应输入模态扣除缓存部分                                                     |
| Gemini 输出模态            | `candidatesTokensDetails[modality=TEXT/AUDIO/IMAGE].tokenCount`                              |
| Gemini 工具输入            | `toolUsePromptTokenCount` 及相关拆分仅作现有诊断或审计信息，不进入本 JSON、Token 费用、输入总量或 TPM                      |
| service tier           | 保留响应侧实际值与请求侧值的区别，留在既有记录位置，不进入本 JSON；差异计费后续适配                                                 |


### 固定 JSON 结构

```json
{
  "schema_version": 1,
  "tokens": {
    "input": {
      "text_input": 0,
      "image_input": 0,
      "audio_input": 0,
      "video_input": 0,
      "document_input": 0
    },
    "output": {
      "text_output": 0,
      "audio_output": 0,
      "image_output": 0,
      "reasoning_output": 0,
      "accepted_prediction": 0,
      "rejected_prediction": 0
    },
    "cache": {
      "read_cache": 0,
      "write_cache": 0,
      "write_cache_5m": 0,
      "write_cache_1h": 0
    }
  }
}
```

1. 顶层只允许 `schema_version`、`tokens`；`tokens` 只允许 `input`、`output`、`cache`。全部示例字段必须存在，不允许额外字段。
2. 当前 `schema_version` 为整数 `1`；全部 Token 值为非负整数，不接受字符串、浮点数、`null` 或省略。
3. 缺失的可选拆分记 `0`；文本输入、文本输出属于归一化结果，不要求上游另外返回同名文本字段。
4. 不写入 quota、单价、倍率、分组、供应商、service tier、费用、错误信息或请求元数据。
5. 损坏 JSON、必填字段缺失、类型错误、负数、未知版本、未知字段和不成立的总量关系进入明确错误路径，不得静默裁剪或补零通过校验。

### 字段定义与唯一汇总公式

```text
text_input = 普通输入总量
           - image_input - audio_input - video_input - document_input

text_output = 上游输出总量 - audio_output - image_output

普通输入总量 = text_input + image_input + audio_input
             + video_input + document_input

输入侧总量 = 普通输入总量 + read_cache + write_cache
输出总量 = text_output + audio_output + image_output
处理总量 = 输入侧总量 + 输出总量
上下文档位用量 = 输入侧总量
TPM = 最近 60 秒纳入统计的消费记录的处理总量之和
```

1. 输入模态数量使用已归一化结果；上游明确提供缓存模态时先从对应模态扣除缓存。
2. `text_output` 包含推理，不包含单独记录的音频和图片；`reasoning_output` 是其中拆分，不能再次计入总量或费用。
3. accepted/rejected prediction 只作审计拆分，不额外增加输出总量或费用。
4. `write_cache_5m`、`write_cache_1h` 是 `write_cache` 的子集，不在输入总量中再次相加。
5. 只有输入总量、没有缓存和模态拆分时，`text_input` 等于普通输入总量；只有输出总量、没有独立音频或图片拆分时，`text_output` 等于输出总量。
6. 计费内存结果、落库 JSON 和读取端按上述公式还原的总量一致；不得通过丢弃总量或重复相加满足字段展示。

### 缓存分档与信息缺失

1. 有缓存写入总量、但上游未返回 5m/1h 分档时，`write_cache_5m = write_cache`，`write_cache_1h = 0`。
2. 上游明确返回分档时保留分档值，包括显式 `0`；只返回一个分档时另一个记 `0`。必须满足 `write_cache_5m + write_cache_1h <= write_cache`。
3. 分档之和与总量的差值为未分档写入，按 5m 创建价格结算；缓存总量与分档不得重复计费。
4. 按上游实际返回的数据和本文公式计算。缺少可选拆分时不猜测隐藏模态分布，也不单纯因此拒绝结算；已有总量必须保留。
5. 上游有明确缓存模态数据时精确扣除；缺少缓存模态数据时不得自行假定缓存全部属于文本、音频或其他模态。
6. 缺少可选明细与数据矛盾分别处理。缓存超过输入、已知独立模态无法满足总量关系、分档超过总量等情况必须显式报错，不得把负数截成 `0`。
7. 整体无 usage、采用估算 usage、上游真实 usage 分别按既有行为处理并可诊断，不得把缺失 usage 伪造成已确认的全零用量。

## 验收环节三：计费逻辑

### 阶段 2：计费切换到归一化结果

1. 实际结算与日志序列化使用同一次请求内存中的 `BillingUsage`；不得从旧列、日志 JSON 或客户端转换后的 usage 反推本次计费用量。
2. 移除实际计费和展示路径中的供应商语义猜测、重复缓存减法、重复音频减法和前端普通输入反推逻辑。
3. 同一 Token 不得同时按父组件和已独立计价的子组件收费；reasoning 和 prediction 不增加第二份输出费用。
4. 普通 relay、Claude 原生、Bedrock、OpenRouter 对应路径、OpenAI Chat、Responses、Gemini、audio、realtime、WSS 全部接入。
5. 工具费、图片生成调用费、文件检索费、定制音色、模型测试费和违规费维持各自适用路径；同请求的 Token 部分只来自归一化结果。
6. 新旧公式对拍仅在等价配置、旧公式语义正确时要求额度一致；差异必须定位并记录为旧错误修复或新实现缺陷，不得直接吸收差异。


| 场景                           | 验收要求                       |
| ---------------------------- | -------------------------- |
| 非流式与流式                       | 等价上游用量产生相同语义、JSON 和结算结果    |
| 流式累计快照与增量                    | 按来源正确累计，重复快照不重复增加 Token    |
| Claude 原生、Bedrock、OpenRouter | 等价 Claude 用量按同一套规则归一化      |
| audio、realtime、WSS           | 每个实际消费入口均完成计费、落库和统计接入      |
| 失败重试与重复处理                    | 不重复结算同一笔消费；实际独立消费按既有规则处理   |
| 预扣、补扣、退款                     | 最终净扣款与实际结算一致，失败和中断正确处理预扣额度 |
| 无 usage、估算、归一化失败             | 分别可诊断，保持对应账务处理，不伪造成功       |
| 缓存、模态、reasoning、prediction   | 数量与费用均不重复，包含关系与固定公式一致      |
| Token 与独立费用并存                | 分别可解释，不丢失也不重复计费            |
| 客户端响应                        | 协议转换、流式输出和 usage 语义保持既有行为  |


### 阶段 3：组件化价格表

1. 价格计划、价格组件使用新增关系表或独立列承载，不改写旧列为 JSON，不在旧列拼接存储新结构。
2. 组件覆盖 text/image/audio/video/document 输入、text/audio/image 输出、缓存读取、缓存写入 5m/1h；保留按次、免费、上下文分档和分组倍率能力。
3. reasoning 复用文本输出价格，只作展示拆分，不形成额外费用。
4. 旧 `model_ratio`、`completion_ratio`、缓存及音频倍率、按次价格转换为等价配置后额度不变；由旧配置转换的价格可恢复为等价旧配置。
5. 新价格、旧配置映射、适用端点、分组、上下文区间和生效时间按明确的匹配规则选择；接口与实际结算采用一致规则。
6. 整个模型缺价、某个组件缺价、显式零价和免费模式分别验收；不把缺价当作免费，也不把合法零价当作未配置。
7. 管理端保存具有权限校验、审计日志和服务端数据校验，覆盖单位、汇率、精度、取整、分组倍率及分档边界；保存后缓存刷新。
8. 前端支持按 Token、按次、免费模式和组件、上下文分档编辑，包含校验提示、空态与中英文 i18n。

### 阶段 4：按价格表结算

1. 归一化数量与实际生效组件逐项匹配，实际生产结算必须经过统一价格选择入口。
2. 缺失组件按明确规则查找适用父组件、低优先级计划或旧配置；全部适用规则都无法提供价格时进入清晰错误路径，不静默按 `0` 收费。
3. 上下文档位只按普通输入＋缓存创建＋缓存读取匹配，不含输出；相同输入不得因输出变长而改变档位。
4. 上下文区间边界、命中后的计价方式与价格配置一致，覆盖边界值及跨档样例；不把上下文档位与 service tier 混为同一能力。
5. Decimal 中间结果不提前取整；最终 quota 按明确且一致的规则取整，并有精度与边界测试。
6. 日志保留实际生效的价格组件、数量、分组倍率、上下文档位、价格来源及其他必要结算快照；修改价格后历史账单仍可解释。
7. `Quota` 是实际结算结果，不由 `billing_details` 或当前价格反推；Token 费用、独立费用、最终净扣款与快照可以核对。
8. 预扣、补扣、退款、失败重试、重复回调及并发处理保持原子性和适用的幂等行为，不重复扣款或退款。

## 验收环节四：使用日志、统计与导出（阶段 5）

1. 复用现有日志 API；必要的 Token 总量由服务端从 `billing_details` 投影，不新增专用 Token 反馈接口，不恢复旧数据库列。
2. 前端集中解析器供表格、tooltip、详情弹窗复用；字段名称及包含关系与本文 schema 一致。
3. 日志展示、TPM、Token 消耗统计、相关汇总与导出全部改用 `billing_details`，采用本文唯一汇总公式，不从 `Other`、旧列或价格快照回退。
4. 已有汇总表和缓存可继续承载统计结果，但其 Token 数据生成来源必须切换到新结构；历史汇总不得与迁移后的数据重复累计。
5. 金额读取 `Quota`，价格解释读取当时结算快照，不按当前价格重算历史账单；RPM 继续按请求记录计数。
6. TPM 使用最近 60 秒消费记录的处理总量；其他时间范围的 Token 汇总按对应筛选区间计算，缓存分档、reasoning、prediction 不重复相加。
7. 迁移后的历史日志与新日志同屏展示正确；筛选、排序、分页、导出、权限及统计查询不依赖已删除的列。
8. 无 Token 明细显示明确空态；合法全零 JSON 显示有效零值；损坏 JSON、未知版本、缺字段、非法数值显示明确错误，不伪装成零用量，不启发式恢复。
9. `Other` 为空时，有效的 `billing_details` 仍可独立展示；Token 字段裁剪不得导致客户端重新猜测或回退旧来源。
10. 管理员和普通用户可见字段由服务端执行权限及字段设置裁剪；admin-only 信息不得下发普通用户，列表、详情和导出规则一致。
11. 保留工具费、违规费等独立费用展示及既有诊断能力；已有 service tier 记录仅按实际记录展示，不以此认定差异计费已完成适配。
12. 同一条记录避免重复 JSON 解析；统计不得引入每请求逐条查询或无界加载全部日志，需提供代表性数据量下的查询验证。
13. 新增文案补齐中英文 i18n；列表遵守 `DataTablePage` + `SectionPageLayout` 规范。
