# AGENTS.md 完全使用指南

> 一份写给所有 AI 编程智能体的项目说明书——让智能体第一次走进你的代码仓库，就知道该做什么、不该做什么。

---

## 序言：为什么世界需要 AGENTS.md

AI 编程智能体这几年从"偶尔能帮忙"进化到了"几乎可以独立完成中型任务"的程度。工具越来越强，但一个尴尬的问题始终存在：**智能体每次走进你的仓库，都像一个新入职、没有交接文档、也没人带他逛一圈的实习生。**

README.md 是写给人看的——快速上手、项目介绍、贡献指南。但 README 不会告诉智能体"这个项目用 pnpm 不用 npm""测试要跑 `pnpm turbo run test --filter <package>`""提交前必须过 lint"。这些信息过去散落在同事的脑子里、聊天记录里、某份没人维护的 onboarding 文档里。

这就是 `AGENTS.md` 诞生的原因——**一份专门写给智能体读的项目说明书。**

它不是 README 的替代品，而是补充品。它收录的是那些"对人类贡献者不重要、但对智能体至关重要"的上下文：构建步骤、测试命令、代码规范、安全注意事项。

这份指南从最基础的概念讲起，一路深入到单体仓库的嵌套策略、指令预算管理、渐进式披露，再到实际编写与重构的全流程。无论你是第一次听说 AGENTS.md，还是已经维护了一年却发现文件越来越臃肿，都能从中找到答案。

---

## 第一章 认识 AGENTS.md

### 1.1 它是什么

`AGENTS.md` 是一个纳入 Git 版本管理的 Markdown 文件，用来定制 AI 编程智能体在你的代码仓库中的行为方式。你可以把它理解为**写给智能体的 README**——一个专门的、可预测的位置，用来提供上下文和指令，帮助智能体高效地参与你的项目。

从技术角度说，它位于对话历史的最顶端，紧贴在系统提示词下方。它是智能体基础指令与实际代码库之间的一层配置桥梁。

这份文件可以包含两类指引：

**个人层面**——你的提交风格偏好、你偏好的代码模式、你个人的工作习惯。

**项目层面**——这个项目是做什么的、用哪个包管理器、你的架构决策、测试如何运行、安全上有何禁忌。

在没有 `AGENTS.md` 的日子里，智能体只能靠猜：猜你用什么包管理器，猜你的测试框架是 Jest 还是 Vitest，猜你的提交规范是 Conventional Commits 还是团队自定义格式。猜对了皆大欢喜，猜错了就是一连串的返工。更糟糕的是，这些"该告诉智能体的话"过去要么不存在，要么被硬塞进 README 里——把人类读者淹没在技术细节中，同时又不够完整、不够精准。`AGENTS.md` 的存在，让这一切有了专门的归宿。

### 1.2 与 CLAUDE.md 的关系

需要特别说明的是，Claude Code 使用的是 `CLAUDE.md` 而非 `AGENTS.md`。这两者在格式和用途上高度一致，你可以通过软链接让它们指向同一份内容，从而确保所有工具行为保持一致：

```bash
# 从 AGENTS.md 软链接到 CLAUDE.md
ln -s AGENTS.md CLAUDE.md
```

部分工具（如 Gemini CLI）则通过配置文件中的 context 字段来指定加载哪个文件，灵活性很高。

## 第二章 为什么一份糟糕的 AGENTS.md 比没有更糟

### 2.1 膨胀的反馈循环

在实际项目中，一个非常普遍、也非常危险的自然反馈循环会反复出现：

1. 智能体做了某件你不喜欢的事
2. 你在 `AGENTS.md` 里加一条规则去阻止它
3. 几个月里重复了几百次
4. 文件变成了一团无法梳理的"泥球"

不同的开发者往里塞相互冲突的意见，没有人做整体风格梳理。最终你会得到一坨无法维护、实际上还会拖垮智能体表现的烂摊子。

另一个罪魁祸首是**自动生成的 AGENTS.md 文件**。建议非常明确：永远不要用初始化脚本去自动生成你的 `AGENTS.md`。这类脚本会把一堆"在大多数场景下有用"的东西灌进文件，而这些内容本该用渐进式披露来处理。生成式文件追求的是"全面"，而不是"克制"——而克制，才是这份文件的灵魂。

### 2.2 指令预算

前沿的推理型大模型，大致能稳定遵循约 150–200 条指令。小模型能关注的指令数量少于大模型，非思考型模型能关注的指令数量少于思考型模型。

你的 `AGENTS.md` 中的**每一个 token，都会在每一次请求里被加载**，无论它当下是否相关。这就造成了一个硬性的预算约束：

| 场景 | 影响 |
| --- | --- |
| 精简、聚焦的 `AGENTS.md` | 留给任务专属指令的 token 更多，智能体表现更佳 |
| 臃肿、庞大的 `AGENTS.md` | 留给实际工作的 token 更少，智能体变得糊涂 |
| 大量无关指令 | token 浪费叠加智能体分心，表现显著下降 |

综合来看，这意味着一个反直觉的结论：**理想的 `AGENTS.md` 文件应当尽可能小。**

### 2.3 过时的文档会主动污染上下文

文档过时得非常快。对人类开发者来说，过时的文档只是令人烦恼，因为人通常有足够的记忆储备，会对糟糕的文档保持怀疑。而对那些每次请求都重新读取文档的 AI 智能体来说，陈旧信息会**主动污染**上下文。

当你去记录文件系统结构时，这一点尤其危险。文件路径时刻在变。如果你的 `AGENTS.md` 写着"认证逻辑位于 `src/auth/handlers.ts`"，而那个文件被重命名或移动了，智能体就会信心十足地找错地方。

**与其记录结构，不如描述能力。** 给一些"东西大概可能在哪""项目整体长什么样"的提示，让智能体在规划阶段自己去生成即时文档。

领域概念（比如"组织 organization" vs "群组 group" vs "工作区 workspace"）比文件路径更稳定，因此更适合记录下来。但即便这些，在快速演进的 AI 辅助代码库里也会漂移——下手要轻。

## 第三章 编写规范：什么该写，什么不该写

### 3.1 最小必要内容

对什么能放进根 `AGENTS.md`，要毫不留情。以下几项是绝对的最低限度：

- **一句话项目描述**——作用类似一个基于角色的提示词，锚定智能体的职责范围
- **包管理器**——如果不是 npm；或者用 `corepack` 来自动处理
- **构建/类型检查命令**——如果不是标准命令

说实话，就这些。其他一切都该放到别处。

### 3.2 一句话项目描述

这一句话给智能体提供了"为什么在这个仓库里工作"的上下文，锚定了它所做的每一个决策：

```markdown
这是一个用于无障碍数据可视化的 React 组件库。
```

这就是地基。智能体立刻理解了它的职责范围——它不会给你引入一个不关心可访问性的图表库，也不会写出忽略 ARIA 标签的组件。

### 3.3 包管理器规范

如果你在一个 JavaScript 项目里、且用的是 npm 以外的东西，明确告诉智能体：

```markdown
本项目使用 pnpm workspaces（工作区）。
```

如果不说，智能体可能会默认用 `npm`，从而生成错误的命令、甚至破坏你的 lock 文件。

`corepack` 也很棒——你可以用它让系统自动处理包管理器警告，从而省下宝贵的指令预算。

### 3.4 构建与测试命令

智能体需要知道如何验证它写下的代码。如果你的命令不是行业标准的 `npm run build` / `npm test`，就写清楚：

```markdown
## Setup commands
- Install deps: `pnpm install`
- Start dev server: `pnpm dev`
- Run tests: `pnpm test`
```

更精细的场景下，可以给出子包级别的测试指令：

```markdown
## Testing instructions
- Run `pnpm turbo run test --filter <project_name>` to run every check defined for that package.
- From the package root you can just call `pnpm test`.
- To focus on one step, add the Vitest pattern: `pnpm vitest run -t "<test name>"`.
```

### 3.5 代码风格

如果你的项目有非显而易见的代码风格约定，可以简要列出。但请注意"简要"二字——详细的规范应该拆到独立文件中（详见第四章）：

```markdown
## Code style
- TypeScript strict mode
- Single quotes, no semicolons
- Use functional patterns where possible
```

### 3.6 其他有价值的板块

以下内容只要"你会告诉一个新入职同事"，就值得写进来：

- **提交信息 / PR 规范**——如 `Title format: [<project_name>] <Title>`
- **安全注意事项**——哪些操作绝对不能做、哪些密钥不能提交
- **部署流程**——尤其是非标准的部署步骤
- **大型数据集说明**——数据在哪里、如何获取、如何处理

### 3.7 什么不该写

这些内容请坚决删除或移走：

- **冗余的指令**——智能体已经知道的（比如"写干净的代码"）
- **过于模糊、无法落地的**——比如"保持高质量"
- **过于显而易见的**——比如"JavaScript 文件以 .js 结尾"
- **相互矛盾的指令**——同一件事给了两个相互冲突的要求
- **精确的文件路径**——它们会过时，用能力描述替代
- **一次性任务的记录**——这些不属于长期配置

## 第四章 渐进式披露：AGENTS.md 的核心哲学

### 4.1 核心思想

与其把所有东西都硬塞进 `AGENTS.md`，不如使用**渐进式披露（Progressive Disclosure）**：只给智能体此刻需要的东西，在需要时再指引它去别的资源。

智能体在遍历文档层级结构时非常快，它们对上下文的理解力足以找到自己需要的内容。这意味着你不必担心"智能体找不到详细规范"——只要给它面包屑，它会自己跟过去。

### 4.2 把语言相关的规则移到独立文件

如果你的 `AGENTS.md` 现在是这样写的：

```markdown
始终使用 const 而不是 let。
永远不要使用 var。
尽可能用 interface 而不是 type。
使用严格的空值检查（strict null checks）。
使用 const 断言而不是字面量类型。
避免使用 any，用 unknown 替代。
……
```

那就把它移到一个独立文件里。在你的根 `AGENTS.md` 中只需写一句：

```markdown
关于 TypeScript 规范，参见 docs/TYPESCRIPT.md。
```

注意这里的语气——没有"始终"、没有全大写的强迫语气，只是一句对话式的引用。

这样做的好处是三重的：

- TypeScript 规则只在智能体写 TypeScript 时才加载，节省 token
- 其他任务（CSS 调试、依赖管理）不会浪费 token 在无关规范上
- 文件保持聚焦，且能在模型更迭间轻松移植

### 4.3 嵌套式渐进披露

你还能走得更深。你的 `docs/TYPESCRIPT.md` 可以引用 `docs/TESTING.md`，从而构建一棵可发现的资源树：

```text
docs/
├── TYPESCRIPT.md
│   └── 引用 TESTING.md
├── TESTING.md
│   └── 引用具体的测试运行器
└── BUILD.md
    └── 引用 esbuild 配置
```

你甚至可以链接到外部资源，比如 Prisma 文档、Next.js 文档等。智能体会高效地遍历这些层级结构，按需拉取知识。

### 4.4 智能体技能

许多工具支持"智能体技能（Agent Skills）"——智能体可以调用的命令或工作流，用来学习如何完成某项具体任务。这是渐进式披露的另一种形式：智能体只在需要时才拉取知识，而不是一开始就把所有规范塞进上下文。

如果你发现自己有大量"操作指南"性质的内容（比如"如何发布新版本""如何调试本地数据库"），考虑把它们封装为技能，而不是写进 `AGENTS.md`。

## 第五章 单体仓库中的分层策略

### 5.1 嵌套的 AGENTS.md

你并不局限于根目录下的单个 `AGENTS.md`。你可以把 `AGENTS.md` 放在子目录里，它们会**与根级别的配置合并**。智能体会自动读取目录树中最近的文件，因此最近的文件优先级最高，每个子项目都可以携带专属指令。

这对单体仓库来说非常强大。以 OpenAI 的主仓库为例，截至撰写时它拥有 88 个 `AGENTS.md` 文件。

### 5.2 分层内容规划

| 层级 | 应放置的内容 |
| --- | --- |
| **根目录** | 单体仓库的目的、如何导航各个包、共享工具（如 pnpm workspaces）、全局构建命令 |
| **包级别** | 该包的目的、具体技术栈、包专属的规范、包内测试命令 |

根 `AGENTS.md` 示例：

```markdown
这是一个包含 Web 服务和 CLI 工具的单体仓库。
使用 pnpm workspaces 来管理依赖。
各包的具体指引请参见对应包的 AGENTS.md。
```

包级别的 `AGENTS.md`（位于 `packages/api/AGENTS.md`）：

```markdown
这个包是一个使用 Prisma 的 Node.js GraphQL API。
API 设计模式请遵循 docs/API_CONVENTIONS.md。
```

### 5.3 不要给任何层级过载

智能体在上下文中会看到所有合并后的 `AGENTS.md` 文件。让每一层都聚焦在"该层级真正相关"的内容上。如果一条规则只对某个包有意义，就绝对不要放到根目录里。

## 第六章 从零开始：完整示例

### 6.1 最小可用版本

如果你刚起步，这是最小但仍然有效的 `AGENTS.md`：

```markdown
# AGENTS.md

这是一个用于实时协作白板的 TypeScript 全栈应用。
使用 pnpm 作为包管理器。
```

三行。但这三行已经让智能体知道：它在哪、用什么工具、这个项目的核心是什么。

### 6.2 推荐的完整版本

以下是一个中型项目典型的、结构良好的 `AGENTS.md`：

```markdown
# AGENTS.md

## Project overview
这是一个用于无障碍数据可视化的 React 组件库，
支持 SSR 和树摇优化。

## Setup commands
- Install deps: `pnpm install`
- Start dev server: `pnpm dev`
- Run tests: `pnpm test`

## Code style
- TypeScript strict mode
- Single quotes, no semicolons
- Functional patterns preferred
- 详细规范参见 docs/CODE_STYLE.md

## Testing instructions
- Find the CI plan in the .github/workflows folder.
- Run `pnpm turbo run test --filter <project_name>` to run checks for a package.
- After moving files or changing imports, run `pnpm lint --filter <project_name>`.
- Add or update tests for the code you change, even if nobody asked.

## PR instructions
- Title format: [<project_name>] <Title>
- Always run `pnpm lint` and `pnpm test` before committing.

## Dev environment tips
- Use `pnpm dlx turbo run where <project_name>` to jump to a package.
- Check the name field inside each package's package.json to confirm the right name.
```

### 6.3 配套的文档树

配合上面的根文件，你的 `docs/` 目录可能长这样：

```text
docs/
├── CODE_STYLE.md      # 详细的代码风格规范
├── TESTING.md         # 测试模式与约定
├── ACCESSIBILITY.md   # 无障碍实现指南
└── DEPLOYMENT.md      # 部署流程
```

每个文件内部还可以进一步引用更细分的资源，形成渐进式披露的层级结构。

## 第七章 重构：拯救一份臃肿的 AGENTS.md

### 7.1 诊断信号

如果你观察到以下任何一种情况，说明你的 `AGENTS.md` 需要重构了：

- 文件超过 100 行且还在增长
- 不同开发者往里加了相互矛盾的规则
- 智能体开始忽略你写的某些指令
- 你自己也说不清文件里到底写了什么
- 每次遇到智能体犯错，你的第一反应是"再加一条规则"

### 7.2 重构提示词

如果你想把它重构成渐进式披露的结构，把下面这个提示词复制粘贴进你的编程智能体：

```markdown
我想让你按照渐进式披露的原则重构我的 AGENTS.md 文件。
请遵循以下步骤：

1. **找出矛盾**：识别任何彼此冲突的指令。对每处矛盾，
   问我想要保留哪个版本。

2. **识别要点**：只提取真正属于根 AGENTS.md 的内容：
   - 一句话项目描述
   - 包管理器（如果不是 npm）
   - 非标准的构建/类型检查命令
   - 任何对每一项任务都真正相关的东西

3. **归类其余内容**：把剩余的指令组织成逻辑分类
   （例如 TypeScript 规范、测试模式、API 设计、Git 工作流）。
   为每个分类创建一个独立的 Markdown 文件。

4. **创建文件结构**：输出：
   - 一个最小化的根 AGENTS.md，包含指向各独立文件的 Markdown 链接
   - 每个独立文件及其相关指令
   - 一个建议的 docs/ 文件夹结构

5. **标记待删除项**：识别任何满足以下条件的指令：
   - 冗余的（智能体已经知道）
   - 过于模糊、无法落地的
   - 过于显而易见的（比如"写干净的代码"）
```

### 7.3 决策矩阵：内容该放哪里

每次准备往 `AGENTS.md` 里加东西时，先问自己：它该放在哪里？

| 位置 | 何时使用 |
| --- | --- |
| 根 `AGENTS.md` | 对仓库里**每一项**任务都相关的信息 |
| 独立文件 | 只对某一领域相关（TypeScript、测试等） |
| 嵌套的文档树 | 可以按层级组织的内容 |
| 嵌套的 `AGENTS.md` | 只对某个子包相关的信息 |
| 智能体技能 | 操作流程类知识（发布、调试等） |
| 不写 | 冗余、模糊、显而易见的内容 |

---

## 结语

理想的 `AGENTS.md` 是**小巧、聚焦、并指向别处**的。它给智能体刚好足够的上下文来开工，同时留下通往更详细指引的面包屑。

其他一切都活在渐进式披露里：独立文件、嵌套的 `AGENTS.md` 文件、智能体技能。

这能让你的指令预算保持高效、让智能体保持专注，并让你的配置随着工具与最佳实践的演进而始终面向未来。

记住核心原则：**克制是美德，聚焦是力量。**

写好它，然后放手让智能体去发挥。
